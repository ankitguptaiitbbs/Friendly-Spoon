# Ashmal — A Greedy Tale of Two Ends

> *A story about choices that look local, but shape a global outcome.*

---

## The World

You are handed **n strings**.
They arrive **one by one**, in a fixed order.

You start with **nothing** — an empty string `s`.

At each step `i`, you must make a binary choice:

* put `a[i]` at the **front** of `s`, or
* put `a[i]` at the **back** of `s`

Once placed, **the choice is permanent**.
There is no rewind. No rearranging later.

Your mission is simple to state and hard to get wrong:

> After all `n` steps, make `s` **lexicographically smallest possible**.

This is *Ashmal*.

---

## Lexicographic Gravity

Lexicographic order behaves like gravity:

* the **earlier** characters matter more
* a smaller prefix **dominates everything** that follows

If two strings differ at position `k`,
whatever happens after `k` is irrelevant.

So the problem is not about the whole string.
It’s about **who gets to speak first**.

---

## The Naïve Temptation

At step `i`, you are staring at two futures:

```text
Front: a[i] + s
Back:  s + a[i]
```

Both are legal.
Only one is optimal.

The dangerous instinct is to overthink:

* simulate deep futures
* try DP
* attempt clever reordering

But the problem is already constrained.
The strings arrive in order.
Your only freedom is **left or right**.

This is not a DP problem.
This is a **greedy one**.

---

## The Greedy Insight (The Entire Problem)

At step `i`, ask one question:

> Which string is smaller **right now**?

```text
Is (s + a[i]) > (a[i] + s) ?
```

* If **yes** → prepend `a[i]`
* If **no**  → append `a[i]`

That’s it.

No lookahead.
No backtracking.
No regret.

Why does this work?

Because lexicographic order is **prefix-dominated**.
If `a[i] + s` wins now, it will win forever.
Future additions only touch the suffix.

The greedy choice is **globally optimal**.

## Walking Through the Code

Let’s read the implementation as a story, not syntax.

```cpp
string s = words[0];
```

We begin with the first word.
No choice yet. The world is born.

---

```cpp
for (int i = 1; i < n; i++) {
```

Every iteration is a fork in the road.
Two futures. One decision.

---

```cpp
if (s + words[i] > words[i] + s) {
    s = words[i] + s;
} else {
    s += words[i];
}
```

This is the heart of Ashmal.

You literally compare both possible realities
and choose the smaller universe.

No heuristics.
No guessing.
Just truth.

---

## Why This Is Safe

### ✔ Deterministic

Same input → same output.

### ✔ Efficient

Total string length ≤ 4000.
Each comparison is linear.
This easily fits the limits.

### ✔ Minimal State

One string `s`.
One decision per step.

The algorithm respects the problem’s constraints
instead of fighting them.

---

## Mental Model (Cache This)

Think of `s` as a **rope**.
Each new word is a **block**.

At every step, you ask:

> Which side makes the rope lexicographically lighter?

You always attach the block
where it causes the **least disturbance at the front**.

Once attached, it becomes part of the rope forever.

---

## Final Thought

Ashmal looks like a string problem.
It’s actually a **decision-order problem**.

The trick is realizing that:

* the future cannot fix a bad prefix
* local lexicographic wins compound
* greedy is not a shortcut — it’s the solution

This is clean code.
This is clean logic.

And when someone reads your solution later,
they won’t ask *why it works*.

They’ll just nod.
